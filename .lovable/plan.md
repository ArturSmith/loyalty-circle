## Goal

A customer scans a business QR, taps **Add to Google Wallet**, and the loyalty card lands in their Google Wallet — no ClubCarder account. Stamps added by the business update the pass automatically. The pass carries a link so the customer can later create an account and keep the card.

## How Google Wallet works here (short version)

- We define a **Loyalty Class** (one per card template — branding, logo, colours, program name) and a **Loyalty Object** (one per customer card — points, barcode, state).
- "Add to Wallet" is a signed JWT link generated by our server with a Google service account key. No user login, no popup.
- When a stamp is added, our server PATCHes the loyalty object via the Google Wallet REST API; the pass in the customer's phone updates within seconds.
- The pass's barcode holds the card instance ID, so the business scanner works exactly as it does today.

## What you need to provide (one-time, free)

1. A Google Cloud project with the **Google Wallet API** enabled.
2. A **service account** + JSON key (this is the signing key).
3. A **Google Wallet Issuer account** (issuer ID) via the Google Pay & Wallet Console, with the service account granted issuer access.

I'll store the key material as backend secrets: `GOOGLE_WALLET_ISSUER_ID`, `GOOGLE_WALLET_SA_EMAIL`, `GOOGLE_WALLET_SA_PRIVATE_KEY`. Until those exist, everything below still builds — the wallet button just stays hidden.

## Data model changes

`card_instances`:
- `customer_id` becomes nullable (anonymous cards).
- `anon_secret` (uuid) — proves ownership of an anonymous card from the pass link.
- `google_object_id` (text, unique) — the Wallet object.
- `claimed_at`.

`card_templates`:
- `google_class_id` (text) — created lazily the first time someone adds that card to Wallet.

RLS/trigger updates:
- Anonymous instances are never selectable by `anon`/`authenticated` directly; all reads go through server functions.
- `add_stamp` keeps the same authorization (business owner only) but stops assuming `customer_id` is set.
- Claiming: a server function trades a valid `anon_secret` for `customer_id = auth.uid()`.

## Server work (TanStack server functions + one public route)

- `src/lib/googleWallet.server.ts` — RS256 JWT signing via WebCrypto, class create/update, object create, object PATCH. No Node-only deps.
- `src/utils/wallet.functions.ts`:
  - `createWalletPass({ templateId })` — public (unauthenticated). Creates an anonymous instance (rate-limited per IP), ensures the loyalty class exists, creates the object, returns the `https://pay.google.com/gp/v/save/<jwt>` URL.
  - `claimAnonymousCard({ instanceId, secret })` — authenticated; attaches the card to the signed-in user.
- Stamping path: after `add_stamp` succeeds, push the new stamp count / reward text to the Wallet object. Done in a server function called by the scanner so a Wallet failure never blocks the stamp.
- Pass content: program name, business logo, points as `stamps / total`, next reward in the details, QR barcode = instance ID, plus an app link to `/claim/<instanceId>?s=<secret>`.

## UI work

- `/b/$businessId`: add a **Add to Google Wallet** button (official badge asset) next to the existing "Add to my wallet". Shown on Android/Chrome; falls back to the in-app flow elsewhere.
- New `/claim/$instanceId` route: signs the visitor in (or signs them up) and attaches the anonymous card to their account, then lands on `/wallet`.
- Business card detail page: anonymous holders counted in the analytics as "wallet passes".

## Apple Wallet (not in this plan)

Same architecture, but it needs the Apple Developer Program ($99/yr), a Pass Type ID certificate and PKCS#7 pass signing plus an APNs-based update service. Once Google is live, the class/object abstraction above is reused and only the signing/serving layer is added.
